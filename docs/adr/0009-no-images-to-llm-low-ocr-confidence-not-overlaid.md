# 不把圖片送給 LLM；OCR 沒把握的句子在本機擋下、不覆蓋

真實網站第二輪盤點（[#123](https://github.com/yurenju/naruhodo-manga-translator/issues/123)）在正文對白看到 OCR 誤讀造成誤譯、而且譯文蓋上了頁面：半濁音讀成清音（プ→フ）、手寫小字整句讀成另一句通順的日文。只差一個字、讀起來不通的錯字，LLM 會靠上下文自己修回；修不回來的，是錯字本身看起來就像一句合理的日文，只看文字沒有任何線索。

最直接的修法是讓 LLM 看那個 Balloon 的 crop 圖、自己再讀一次。但隱私權政策、README、Web Store 上架文案、官網 FAQ 與外掛裡的資料流說明都承諾**圖片不會離開使用者的電腦，送出去的只有辨識出來的文字**，裁切過的小圖也一樣是圖片。

## 決定

- **任何情況都不把圖片（整頁或 crop）送給 LLM**，包括 Own API Key 與 Hosted Translation。
- **OCR 沒把握的句子在本機擋下。** OCR 解碼時記下每一步 softmax 的最高機率，PageText 每段存「非標點字的最低信心」（標點、符號、長音、`―…〜` 不算）。最低信心 **< 0.25** 的段當成 `unreadable`：不覆蓋，side panel 照常列出原文。Balloon 與 Loose Text 都適用。
- **LLM 判斷是亂碼的段（`unreadable`）也不覆蓋。** 兩者任一成立就是 `unreadable`；LLM 讀得懂，也不會把本機擋下的段改回來。
- 不送候選字、不為了 OCR 的不確定性改翻譯呼叫（①）的 prompt、① 不回傳修正後的原文。

讀者看到的是日文原文，而不是一句看起來通順的錯誤譯文。trace 的 `analyze` 記下每段的最低信心與每頁被門檻擋下的段數，在真實網站上核對用。

## 句尾雜訊剪掉，不整段擋

真實網站盤點看到一句台詞整句沒翻：句尾加了假名注音的名字連同「!!」被讀成「177」，這三個字信心 0.20–0.37，前面 12 個字都是 1.00。「最低信心」只看一個字，於是整段 unreadable；LLM 也回 unreadable，而就算它翻了，上一節的規則也不會把本機擋下的段改回來。

被門檻擋下的段，如果**信心 < 0.5 的非標點字全擠在句尾**，而且前面還留著**至少 4 個**非標點字，就把句尾那段（連同夾在裡面的標點）從原文剪掉，剩下的照常翻譯、覆蓋。剪掉的那段記在 `ocrDropped`，trace 的 `analyze` 也看得到。不可靠的字夾在句子中間、或剪完剩太少，照舊整段 unreadable。

- **為什麼是剪掉，不是改 prompt 讓 LLM 翻可讀的部分。** 把同一頁的 request 原樣重送 3 次（Haiku）：2 次 unreadable，1 次翻成「…喔177！」，把雜訊照抄進譯文。剪掉之後 3 次都正常翻譯。LLM 看不到雜訊，就不會有「靠雜訊編一句話」的風險，也不用改 ① 的 prompt。
- **為什麼只剪句尾。** 這次盤點被門檻擋下的 31 段（離線重跑 manga-ocr 看逐字信心），真正的亂碼不是整段都低，就是低信心的字散在句子中間；只剪句尾時，31 段裡只放行了這一句。允許剪句首的話，廣告標誌（例如句首一個字母不可靠）會被放行。
- **代價。** 被剪掉的字不會翻出來（這一句少了句尾的名字），side panel 的原文也是剪過的版本。

## LLM 的 unreadable 不包括變體表記（#179）

真實網站上，非人類角色用平假名、片假名混用的怪拼法說話（GLOSSARY 的 Stylized Spelling），OCR 信心 0.92–0.98，LLM 卻判成亂碼、不覆蓋。① 的 prompt 因此把 unreadable 限定為「OCR 亂碼」或「劇情上本來就看不懂的字」，並把變體表記列為例外：只把假名統一、去掉拉長音就還原得出每個詞的才算，要改字、補字、猜字的不算，而且**只適用於 Balloon**，Loose Text 照原規則判斷。

不採用「LLM 回 unreadable 又給譯文就採用譯文」的程式判斷：自相矛盾只代表模型不確定，採用它正好會蓋上這份 ADR 要擋的通順錯譯。

離線重送（第二輪 40 個 Page，加上 #179 回報的頁面，Haiku）：只靠 LLM 擋下的 15 段亂碼，擋下比例從舊 prompt 的 83%（10 輪）變成 91%（5 輪）；該頁的 4 句變體表記，被判 unreadable 的比例從約 27%（15 輪）降到 5%（5 輪），沒做到每輪都翻。個別句子有 4 段擋下比例下降（最多一段 90% → 40%，但同一段在舊 prompt 另一次重送只有 40%）；新增被判 unreadable 的都是 OCR 信心 < 0.25、本機已擋的段，原本翻譯正常的句子沒有被擋。口齒不清（しゅごい）要改字才還原得出原詞，不在這個例外裡。試過的另外三版：不限 Balloon 的例外放行了框外的廣告亂碼並編出譯文；加上「字序或句子不通就不算」又把變體表記擋回去。

**已知限制**：Haiku 對同一段的 unreadable 判斷每輪不同，同一個 prompt 兩次重送可以差到 40% 對 90%。少數接近門檻的框外文字仍會偶爾被翻出來；只靠改 prompt 壓不下這種雜訊。

## 被取代的做法：候選字交給 LLM 挑

這份 ADR 原本的決定是「OCR 的不確定性用文字傳過去」：信心低的字在送出的原文裡標出來、附上前幾名候選字，讓 LLM 從候選裡挑出合乎語境的那一個，挑不出就回 `unreadable`；① 並回傳修正後的原文，讓 Notes 與 Prior Pages 用修正後的版本。

[#140](https://github.com/yurenju/naruhodo-manga-translator/issues/140) 的離線實驗（第二輪 40 個 Page、271 段，本機重跑 manga-ocr）推翻了這個做法：

- **候選字修不回來。** 門檻 0.5–0.8、k 3–5、兩版 prompt，共 22 輪重送 Haiku：OCR 很有把握的錯字 22 輪都沒修回也沒擋下；手寫小字的錯例，偏向擋下的 prompt 會連 LLM 原本能自己修回的句子一起擋掉，偏向挑字的 prompt 又幾乎擋不下錯例；另一個錯例每組只有 1/3–1/7 輪擋下，其餘自己編句子。正確的字常常不在前幾名候選裡。
- **還更貴。** 每頁 input tokens 多 20–28%，延遲中位數多 0.2–0.3 s。
- **本機門檻分得開。** 錯例的最低信心 0.17–0.18，正確 Balloon 192 句最低 0.415。門檻 0.25：錯例擋下 2/3，LLM 自修的 4 句 0 句被擋，正確 Balloon 0/192 被擋；Loose Text 有 10/50 被擋，多為廣告或設計字的亂碼。門檻 0.30 會擋到 1 句 LLM 自修的句子。不增加 token 也不增加延遲。

錯例只有 3 個，樣本小；之後真實網站盤點再看到誤擋或漏擋時，回來調整門檻。

## 已知限制

- **OCR 很有把握地讀錯的字擋不到。** 被讀錯的字信心值可能高達 0.998，信心沒有訊號；先接受，等真實網站上再看到才另議。

## 不採用的做法

- **送 Balloon 的 crop 圖給 LLM。** 對手寫字與濁音、半濁音最有效，也能順便讓 LLM 看出角色性別，但違反「圖片不離開電腦」的承諾。要改承諾得先改所有對外文案，而且「只送文字」是外掛隱私定位的核心，不值得為少數誤讀放棄。
- **候選字交給 LLM 挑**：見上一節。
- **只在 prompt 裡要 LLM 懷疑不合語境的句子。** 修不回來的錯字恰好都合乎語境，LLM 沒有可以懷疑的依據。
- **換 OCR 模型。** manga-ocr 已經是開源漫畫 OCR 裡相對好的；換模型要重新驗證偵測、效能與重錄 FakeEngine 的資料（[ADR 0007](0007-browser-tests-fake-the-ocr-engine.md)）。
